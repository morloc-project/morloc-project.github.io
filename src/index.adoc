Morloc composes functions written in different languages under one type
system. You write ordinary Python, {cpp}, R or Rust, give each function a
Morloc type, and compose them; the compiler generates every interface the
composition needs: a command line tool, HTTP, TCP and Unix-socket servers, and
MCP tools.

[.home-features]
--
[.home-feature]
====
*The interface is derived.* From one module derive a command line tool, a server
over HTTP, TCP, and Unix sockets, and a set of MCP tool definitions. Each is
projected from checked types, so none can drift from the functions.
<<derived-interface,More>>
====

[.home-feature]
====
*Scale complexity with a modern functional language.* Morloc supports generics,
higher-order functions, typeclasses, sum types and tail-call optimized recursion
in a fully polyglot setting. <<features,More>>
====

[.home-feature]
====
*Fine grained logging, benchmarking and debugging.* Add hooks to expressions and
monitor their runtime, caching behavior, job submissions, and more. Full
multi-language tracebacks with optional input data capture at failure points.
<<annotations,More>>
====

[.home-feature]
====
*Design with types, reuse across implementations.* Write a test suite or
benchmarking harness once against a type signature and run it against every
language that implements it. <<tests-follow-the-type,More>>
====

[#why.onepage]
== Why Morloc

Every command line tool reimplements the same machinery: argument parsing,
input and output formats, help text, streaming, exit codes. None of it is the
tool's work, each tool solves it its own way, and every other caller -- a
library, a server, a model -- gets another layer on top. Morloc derives that
machinery from the function's type instead of having you write it.

Morloc types name no language, so the function behind a type may be written in
any supported language, or composed from functions written in several. A
library of functions cannot be universal if it is partitioned by language.

[[one-program]]
=== One program

Two functions, in two languages, neither aware of the other. A {cpp} sum:

[source, cpp]
.foo.hpp
----
#pragma once
#include <vector>

double sum(const std::vector<double>& vec) {
    double sum = 0.0;
    for (double value : vec) {
        sum += value;
    }
    return sum;
}
----

and a parallel map in Python:

[source, python]
.foo.py
----
import multiprocessing as mp

def pmap(f, xs):
    with mp.Pool() as pool:
        results = pool.map(f, xs)
    return results
----

Neither file imports anything from Morloc. The Morloc module gives each a type
and composes them:

[source, morloc]
.sums.loc
----
module m (sum, sumOfSums)

import root-py
import root-cpp

source Py from "foo.py" ("pmap")
source Cpp from "foo.hpp" ("sum")

pmap :: (a -> b) -> [a] -> [b]

--' Add up a list of numbers
sum :: [Real] -> Real

--' Add up a list of lists, summing each in parallel
sumOfSums :: [[Real]] -> Real
sumOfSums = sum . pmap sum
----

`.` is function composition, so `sumOfSums` reads right to left: `pmap sum` sums
each inner list in parallel, and the outer `sum` adds the results. The `--'`
lines are docstrings, which the compiler carries into every generated interface.

[source, console]
----
$ morloc make sums.loc
$ ./sums sumOfSums '[[1,2],[3,4,5]]'
15
----

A Python function called a {cpp} function across a process boundary, and you
wrote no binding, no serializer and no argument parser. <<getting-started>>
builds this program up one step at a time.

[[derived-interface]]
The same build is also a command line tool:

[source, console]
----
$ ./sums -h
Usage: ./sums <nexus_options> <command> <command_options>

Commands:
  sum        Add up a list of numbers
  sumOfSums  Add up a list of lists, summing each in parallel

General Options:
  -h, --help  Print help; -hh adds details and examples, -hhh adds schemas
              (nexus options: -h @)
----

and a set of tool definitions a model client can consume:

[source, console]
----
$ ./sums --mcp-tools
{
  "tools": [
    {
      "name": "sum",
      "description": "Add up a list of numbers",
      "inputSchema": {
        "type": "object",
        "properties": {
          "_1": {
            "type": "array",
            "items": {
              "type": "number"
            }
          }
        },
        "required": [
          "_1"
        ],
        "additionalProperties": false
      }
    },
...
----

These are renderings of the types the compiler checked, so they cannot drift
from the functions: rename an argument and every one of them changes on the next
build. The program also serves over HTTP, TCP and Unix sockets (<<clis>>,
<<deploy-serving>>, <<interface-as-data>>).

[[values-cross-boundaries]]
=== Values cross boundaries, not file formats

Here is a second program. A {cpp} function counts every k-length subsequence of
a string and hands back a `std::map<std::string, int>`. A Python function takes
the Shannon entropy of a count table and expects a `dict`. Morloc knows both as
`Map Str Int`, so composing them is an application and nothing else:

[source, morloc]
.kmers.loc
----
module kmers (countKmers, entropy, complexity)

import map-cpp
import map-py

source Cpp from "kmer.cpp" ("count_kmers" as countKmers)
source Py from "entropy.py" ("entropy" as entropy)

--' Count every k-length subsequence
countKmers :: Int -> Str -> Map Str Int

--' Shannon entropy of a count table, in bits
entropy :: Map Str Int -> Real

--' Sequence complexity: the entropy of its k-mer profile
complexity :: Int -> Str -> Real
complexity k seq = entropy (countKmers k seq)
----

Composed inside one program, nothing is ever written to a file or a pipe:

[source, console]
----
$ ./kmers complexity 3 GATTACAGATTACA
2.75162916738782
----

The same declaration reaches past the edge of a program. Each of those
functions is a command too, so the two halves can run as separate processes and
pass the count table between them:

[source, console]
----
$ ./kmers countKmers 3 GATTACAGATTACA
[["ACA",2],["AGA",1],["ATT",2],["CAG",1],["GAT",2],["TAC",2],["TTA",2]]

$ ./kmers countKmers 3 GATTACAGATTACA | ./kmers entropy -
2.75162916738782
----

Two commands built from one declaration agree on the wire form, so neither side
writes a parser; composing inside one program skips the pipe. Data too large for
memory is a handle to a file (`IFile`, `IStream`, `OStream`; see
<<random-access-and-streaming>>) that crosses between languages like any other
value.

[[signature-vs-implementation]]
=== One signature, many implementations

A module may declare a signature with no code and import its implementations;
when several languages implement it, the compiler picks one per call
(<<abstract-modules>>, <<term-polymorphism>>). The standard library is built
this way: `root` declares, `root-cpp`, `root-py`, `root-r` and `root-rust`
implement.

[[tests-follow-the-type]]
Anything written against the signature works for every implementation.
The `vector` module holds its own test suite, written once, in terms of the
abstract module. Each implementation module binds that suite to itself in three
lines:

[source, morloc]
.vector-py/test.loc
----
module test-vector-py (test)

import vector.test (test)
import vector-py
----

[source, morloc]
.vector-cpp/test.loc
----
module test-vector-cpp (test)

import vector.test (test)
import vector-cpp
----

Same tests, same assertions, different code underneath:

[source, console]
----
$ cd vector-py && morloc make -o test test.loc && ./test test
...
All 81 tests pass

$ cd vector-cpp && morloc make -o test test.loc && ./test test
...
All 81 tests pass
----

[[toolboxes]]
=== Tools compose by import

A module compiled into a tool is still a module. A toolbox that takes commands
from two installed modules, `sift` and `stats`, is an import list and an export
list:

[source, morloc]
.tools.loc
----
--' A little toolbox for reading notes
module tools (scan, summarize, histogram)

import sift
import stats
----

Adding a command is an import; removing one is leaving it out of the export
list, and the code behind it is never built. Neither needs a plugin system or
the consent of the modules' authors.

[[annotations]]
=== Caching, logging and placement are annotations

Label a call site, and configure the label in the program's YAML:

[source, morloc]
----
foo xs = expensive_step@slowfn xs
----

[source, yaml]
----
labeled-groups:
  expensive_step: { cache: true }
----

Every call into `expensive_step@slowfn` is now cached on disk. The same
configuration turns on logging and, still in development, sends a call to a
cluster; a `--debug` build records the arguments of every call a failure passes
through. See <<caching>>, <<logging>>, <<execution-contexts>> and <<debugging>>.

[[one-environment]]
=== One environment, solved once

A program declares its languages and packages, and `mim` resolves them all into
one environment. Inside a language, calls are native; across languages, a call
costs a Unix-socket round trip of a few microseconds. That is cheap enough to
split work into small functions instead of monolithic tools, with format parsing
pushed to the edges. <<per-function-environments>> compares this with one
container per task.

[[what-morloc-is-not]]
=== What Morloc is not

Morloc is not a foreign function interface generator. You write no bindings and
the languages never import one another. They run as separate processes and the
compiler generates the traffic between them, which is why adding a language to a
program costs a line rather than a binding layer.

It is not a language you rewrite into. The {cpp}, Python, R, and Rust in a
Morloc program is ordinary code in those languages, with no Morloc imports, no
annotations, and no base class. You keep your editor, your debugger, your
libraries, and your existing code. What Morloc adds is a type and a name.

[#future.onepage]
== Future Directions

[[what-this-makes-possible]]
=== What this makes possible

Everything in <<why>> is already in the compiler. What it is *for* is not built
yet, and I want to be plain about which is which.

If interfaces are derived rather than written, the only artifact worth
publishing is the function itself. That makes a few things possible that are not
possible today:

* *A library indexed by type.* The compiler already knows every exported
  signature. Searching a library by the shape of the function you need, across
  languages, becomes a question of building the index rather than inventing the
  data.

* *Implementations that compete.* One signature, many implementations, with
  shared tests and shared benchmarks deciding between them -- across languages,
  on your data.

* *Composition that is checked rather than trusted.* If two modules typecheck
  against a common environment, they compose, and the compiler proves it where
  they meet. No pairwise integration testing is required, so the guarantee does
  not get more expensive as the library grows.

* *Communities organized by values instead of by language.* Morloc calls these
  *planes*: namespaces that differ not by subject area or language but by what
  their members demand of code -- review, verification, performance, or nothing
  at all. See <<planes-of-libraries>>.

None of that infrastructure exists yet. There is no registry, no type-directed
search, and no plane but the default one.

[[project-status]]
=== Where the project stands

Morloc has been in development for about ten years. I use it for my own work,
but it is not yet widely used by others. The core features are all present. My
current work is the long tail of edge cases and design optimization.

The compiler and basic type system are mostly complete, though the more advanced
types still need work. Workflow features -- provenance management, re-entrancy,
caching, and job deployment -- are working as prototypes, but need refinement
and much broader support. Environment management, dependency handling and
deployment are well developed through `mim`.

Beyond the compiler, the core libraries are slim and need very careful
design. Language support also needs to be streamlined and extended to new
languages. Zig is the next language on my list, though at some point I should
add boring languages like JavaScript.

[[what-i-need]]
=== What I need

I'm looking for people who can:

* *Write a module.* Take your program, give it types, and publish it.
* *Report what breaks.* A bug report is worth more to me than a patch right
  now. Unexpected behavior, a bad error message, a gap in this manual, and
  anything that was harder than it should have been all count.
* *Fix the editor tooling.* Add support for your favorite editor.
* *Bring a language.* Every new language brings fun design questions, and I
  would be happy to work with you on bringing yours into the Morloc ecosystem.
* *Tell me the right way to build a type system.* There is a lot of
  interesting theory to hash through. There's a paper or two buried somewhere in
  all of this.
